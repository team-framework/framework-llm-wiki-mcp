# 작업 및 검증 기록

## 2026-09-29 · 설계와 초기 구현

- 세 가지 토큰 절감 방식을 비교하고 사용자의 선호에 따라 Qdrant 하이브리드 검색을 선택했다. Markdown 정본, 부분 읽기·수정, GitHub Draft PR을 유지한다.
- 웹은 팀 GitHub 인증, Discord 승인은 논의 참여자 누구나, 대화 참여는 멘션·Agent 답글 회신으로 확정했다.
- 서버 정본 157개 문서의 기존 MCP payload를 `o200k_base`로 계산했다. 본문 중복 제거와 compact JSON을 적용한 비교값은 1,015,366 → 566,422 tokens, 44.21% 감소다. 문서마다 한 번씩 읽은 응답 크기 합이며 실제 모델 사용량은 아니다.
- 로컬 TypeScript 검사와 테스트 21개가 통과했다. 검증 범위는 인증, 챗봇 입력·동시 요청·오류 보호, 원문 단락 분할·이어 읽기·경로 보호, 검색·벡터 hash 검증, 부분 수정 충돌 처리다.
- 별도 loopback 추론 서비스에서 Hermes OAuth `gpt-6-luna / low`의 실제 응답을 확인했다. 검증 질문에 `Markdown`으로 답했고 provider usage는 입력 63, 출력 5 tokens였다. 문서 검색 전체 흐름 검증은 아직 아니다.
- 루트 Node 의존성 감사에서 발견한 5건을 호환 범위 업데이트로 처리했고 재검사 결과는 0건이다.
- 기존 운영 서비스와 원래 checkout의 미커밋 변경을 보존하며 별도 작업 폴더·서버 preview에서 구현한다.

다음 검증: 실제 로컬 임베딩·Qdrant 한국어 검색, Fumadocs 빌드·화면·인증, 전체 문서 챗봇, Discord 범위·승인·PR 연결. 진행 상태를 배포 완료로 해석하지 않는다.

## 2026-09-29 · Hermes 문서 챗봇 추론 경로

- `WikiChat`이 제한된 질문·대화 기록·원문 근거를 서버의 OAuth 추론 브리지에 전달하고 출처 목록을 반환한다.
- 기본 모델은 `gpt-6-luna`, 기본 추론 강도는 `low`다. 잘못된 role·초과 입력·동시 요청을 차단하고 provider 오류 원문을 사용자에게 보내지 않는다.
- 브리지는 loopback에서만 수신하며 공유 key를 검사한다. 별도 shell/파일/MCP 도구와 지속 대화 상태를 제공하지 않는다.
- 챗봇 단위 테스트 5개 및 Python 문법 검사 통과. 서버의 실제 OAuth 응답 확인 완료. HTTP 경로·웹 통합 검증은 후속 단계다.

## 2026-09-29 · 단락 검색과 부분 수정

- MCP에 `get_context`, `get_note_outline`, `read_sections`를 추가하고 전체 읽기에서 중복 본문을 제거했다. 키워드와 hash가 일치하는 벡터 후보를 RRF로 합친다.
- 로컬 `wiki:patch`는 dry-run을 기본으로 하며 문서·섹션 hash와 적용 직전 상태를 검사한다. 기존 checkout 밖 경로와 symlink 이탈을 차단한다.
- TypeScript 검사·테스트 21개·diff 공백 검사 통과.
- 같은 157문서 snapshot, `o200k_base`, lexical 검색 8질의에서 도구 payload 210,278 → 47,985 tokens, 77.18% 감소(질의별 중앙 75.67%).
- 대형 문서 20개의 섹션 수정 요청 비교는 406,787 → 93,600 tokens, 76.99% 감소(중앙 74.99%). 실제 LLM 작업 실행 비용 비교가 아니다.
- 신규 문서 20건은 같은 본문을 전달하면 54,898 → 57,175 tokens로 프로토콜 오버헤드가 4.15% 추가됐다. 새 지식 작성 자체가 줄었다고 해석하지 않는다.
- 벡터 검색 품질과 답변 정확도는 별도 평가 전이다. 크기 측정만으로 근거 recall 유지를 주장하지 않는다.

## 2026-09-29 · 실제 벡터 색인

- Qdrant와 CPU 다국어 임베딩을 별도 서비스로 실행했다. 서버 preview에서 정본 157문서, 1,481섹션, 1,785벡터 chunk의 색인이 `ready`에 도달했다.
- 임베딩 계약·원문 hash·manifest를 검사하고 완성된 generation만 alias로 공개한다. 캐시 재사용, 중복 chunk 제거, metadata filter, 실패 시 이전 alias 보존을 테스트했다.
- 한국어·emoji·긴 코드·공백·긴 문자열의 분할 5사례에서 원문 범위 보존과 512-token 입력 제한을 확인했다.
- 독립된 10질의 첫 평가에서 기존 검색·전체 읽기 대비 hybrid 응답 토큰은 74.23% 감소했다. 필수 근거 회수는 6/11에서 7/11이었다. 작은 표본이며 문서별 편중과 현행 수치 누락을 확인해 순위 개선 후 재평가한다.
- 운영 포트, key 구분, 색인 갱신·복구, 읽기 예산을 `docs/operations.md`에 기록했다.

## 2026-09-29 · 검색 순위와 이어 읽기 개선

- 제목·metadata만 일치하는 단락의 가중치를 낮추고, 첫 검색에서 한 문서가 근거를 독점하지 않도록 문서별 두 섹션을 먼저 배치했다. 현행 코드 식별자는 루트의 `_현행_수치.md`에서 직접 일치하는 단락을 우선한다. 과거 질문에는 이 우선순위를 적용하지 않는다.
- 이어 읽기 상태를 10분간 서버에 저장하고 24자 cursor만 반환한다. 원문 변경·만료·서버 재시작에는 다시 검색하도록 오류를 반환한다.
- 공개 합성 문서로 순위·필터·동명 비정본·오래된 벡터·cursor 회귀 테스트 7개를 추가했다. 전체 35개 테스트와 TypeScript 검사가 통과했다.
- 초기 live hybrid의 53,991 tokens·80.65% 감소 결과는 **superseded**다. 반환 근거 65개 중 3개의 문서 hash가 고정 snapshot과 달라 동일 원문 비교로 인용할 수 없다. 당시 warm HTTP 61~108ms도 이 혼합 실행의 관측값이다.
- 같은 10질의·11필수 근거를 고정 snapshot과 별도 벡터 collection으로 재검증했다. 기존 검색과 상위 3문서 전체 읽기는 278,972 tokens, 근거 6/11, 질문 완결 5/10이었다. lexical은 54,448 tokens·80.48% 감소·근거 8/11, hybrid는 54,502 tokens·80.46% 감소·근거 9/11·완결 8/10이었다. 벡터 검색은 lexical보다 54 tokens를 더 사용해 필수 근거 1개를 추가로 찾았다.
- source/index signature·모델 revision·코드·gold·tokenizer provenance와 재현 CLI를 `docs/benchmarks/2026-09-29/retrieval-quality.json`, `scripts/evaluate-retrieval.ts`에 기록했다. 작은 수동 표본의 첫 도구 응답 비교이며 모델 답변 정확도·전체 세션 과금으로 일반화하지 않는다. 누락한 두 자연어 질문은 별도 후속 검색이 필요하다.

## 2026-09-29 · 운영 측정 기반

- 기능·배포 버전·사람/서비스 구분·처리 결과를 SQLite에 기록한다. 신원은 별도 key의 HMAC으로 저장하며 질문·답변·문서 원문을 이벤트에 넣지 않는다.
- 고정 재현 실험, 같은 근거 문서의 전체 읽기 대비 표본 비교, provider 실제 usage를 구분한다. provider가 주지 않은 cache·reasoning 사용량은 null로 남긴다.
- 기능 사용률, D1/D7 완료일 코호트, 검색 후 문서 열기, 답변 피드백, 오류·지연을 정의했다. 사람 수와 재방문에서 서비스·검증 요청을 제외하고 p95는 성공 표본 20건 이상일 때 표시한다.
- 일반 제품 피드백은 사용자가 작성한 설명과 선택한 유형을 별도로 보관한다. 진단 정보는 페이지 경로·화면 크기만 선택해서 첨부한다. 팀원이 검토하며 90일 보존한다.
- 저장 필드 제한·KST 경계·미성숙 코호트·소유권·중복 피드백·표본 분모·계측 오류·만료를 확인한 핵심 테스트 6개가 통과했다. 운영 사용량은 아직 수집 전이다.

## 2026-09-30 · 팀 공용 대화와 화면별 사용 측정

- 웹 대화를 전용 SQLite와 Docker volume에 저장한다. 로그인한 팀원이 같은 대화를 조회하고 이어서 질문하며, 사용량 이벤트 DB와 보존 정책을 분리했다.
- 서버가 저장된 최근 대화를 선택해 모델에 전달한다. 최대 12개 메시지·24,000자로 제한하고 원문 기록은 유지한다. 문맥을 줄인 경우 `history_truncated`로 알린다.
- 버전 검사로 동시 작성을 감지하고, 완료된 요청 ID의 재전송은 모델 호출과 저장을 반복하지 않는다. 실패 시 질문만 남지 않으며, 재시작으로 남은 예약은 만료 후 재시도할 수 있다.
- 인증 없이 또는 Discord 서비스 key로 대화를 읽을 수 없고, 다른 팀원의 답변 평가 ID를 조회할 수 없는지 검증했다. 두 신원의 공용 조회·후속 질문, 재시작 후 복원, 페이지 나눔, 긴 답변 원문 보존을 테스트했다.
- 채팅 작은 창·분할·전용 페이지·공용 기록 열기를 사용 지표에 추가했다. UI 동작은 응답 지연으로 집계하지 않는다. 배포 전후 비교에서 수집 기능이 늘어난 점을 구분한다.
- 서버 전체 테스트 65개와 TypeScript 검사·빌드, Compose 설정 검사가 통과했다. 화면과 운영 배포 검증 결과는 아래에 이어 기록한다.

## 2026-09-30 · MCP 저장소의 자동 스킬 동기화 중단

- [MCP PR #19](https://github.com/team-framework/framework-llm-wiki-mcp/pull/19)는 서버 실행에 필요하지 않은 개발 에이전트 스킬 갱신이었다. PR을 닫고 기존 스킬 파일과 브랜치를 유지했다.
- 중앙 [하네스 PR #30](https://github.com/team-framework/framework-agent-harness-sync/pull/30)을 병합해 정본 위키와 MCP 저장소의 정확한 이름을 제외했다. 다른 저장소와 GitHub App 권한은 유지한다.
- 실제 [자동 동기화](https://github.com/team-framework/framework-agent-harness-sync/actions/runs/36647051417)에는 innolive-client·innolive-server·innolive-ai 작업만 생성됐다. [webhook 배포](https://github.com/team-framework/framework-agent-harness-sync/actions/runs/36647051342)도 성공했으며 실행 중 컨테이너의 제외 정책과 상태를 확인했다.
